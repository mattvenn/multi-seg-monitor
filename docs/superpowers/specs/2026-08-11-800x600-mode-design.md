# 800x600 mode (FPGA-only)

2026-08-11. Follows on from `resolution_discussion.md`, whose §4 "intermediate
step" this originally started as. Confirmed against the user's actual monitor,
which is native 800x600.

## Scope

FPGA target only. `src/config.json`'s `CLOCK_PERIOD` and the ASIC hardening
flow are untouched — this is a bring-up experiment to judge the result on real
hardware before deciding whether to carry it to silicon.

nextpnr-ice40's post-route signoff on the *current* (640x480) design came in at
39.58 MHz against a 40.00 MHz target — a ~1% miss, in the range of normal
seed-to-seed variance and consistent with the 39.14 MHz the design doc recorded
earlier. Close enough that trying it in silicon, per the user, is worth doing
directly rather than blocking on more analysis.

## Timing

VESA DMT 800x600@60, the same standard the existing 640x480@72 mode already
follows exactly:

|        | active | fp | sync | bp | total |
|--------|-------:|---:|-----:|---:|------:|
| H      |    800 | 40 |  128 | 88 |  1056 |
| V      |    600 |  1 |    4 | 23 |   628 |

Pixel clock 40.000 MHz.

## Grid geometry: unchanged

The 12x16 cell and segment rectangle table stay exactly as they are today.
Two mockups redesigning digit size/thickness for a bigger cell (16x20, either
scaled-up-at-the-same-2px-pen or a bolder ~3px pen) were reviewed against the
current digit at the same zoom and rejected — neither read better than what's
already there. So this mode buys more digits, not bigger ones:

- 64 cols x 37 rows = 2368 digits (was 52x30 = 1560)
- 256 B/row — exactly the line buffer's wall (4 buffers x 64 digits x 4 bytes =
  1 kB macro, so `fetch_col` is already a 6-bit field sized for exactly 64).
- Horizontal margin 16 px each side (768 of 800 used) — same proportion as
  today's 640 mode.
- Vertical margin 4 px each side (592 of 600 used) — new. 480 divides evenly
  by 16; 600 does not, so this mode needs an explicit vertical margin the
  current design has never had to check for.
- Pacing: `clocks_per_byte = 16 * 1056 / 256 = 66`, exact.

## RTL changes

- **`VgaSyncGen.v`**: `hc`/`x_px` are hardcoded 10-bit regs. 1056 needs 11
  bits — left alone this silently wraps and breaks hsync. Widen both to 11
  bits. `vc`/`y_px` stay 10-bit (628 fits).
- **`multi_seg_monitor.v`**:
  - `row` and `gen_row` are hardcoded 5-bit (max 31). ROWS-1=36 needs 6 bits.
  - New `MARGIN_Y` localparam and a `cell_y` bound check, alongside the
    existing `cell_x`, gating rendering to the active 592 rows.
  - Localparams: `COLS 52->64`, `ROWS 30->37`, `ROW_BYTES 208->256`.
    `MARGIN_X` recomputes to the same value (16) despite different inputs.
  - `CELL_W`/`CELL_H` (12/16) and the segment rectangle table: unchanged.
- **Untouched**: `line_buffer.v`, `gamma.v`, `stream_in.v`, `seg7_rom.v` — the
  buffer was already sized for exactly 64 cols; nothing here depends on the
  specific resolution.
- **`tt_um_multi_seg_monitor.v`**: update the `VgaSyncGen` instantiation's
  timing parameters.

## Software mirrors

Per CLAUDE.md's blast-radius note, these move together with any geometry or
timing change:

- `tools/segments.py`: `COLS`/`ROWS`/`ROW_BYTES`/`FRAME_BYTES`
  (64/37/256/9472), and a `MARGIN_Y` if `segment_centre`/`segment_pixels`
  assume zero vertical margin.
- `firmware/seg_player.py`: same grid constants, plus `CLOCKS_PER_BYTE=66`,
  `PIXEL_HZ=40_000_000`.
- `test/tb.v` and `test/test_multi_seg.py`: their own copies of the
  timing/grid constants (`H_ACTIVE`/`H_FP`/`H_SYNC`/`H_BP`,
  `V_ACTIVE`/`V_FP`/`V_SYNC`/`V_BP`, `COLS`/`ROWS`/`CELL_W`/`CELL_H`,
  `MARGIN_X`, new `MARGIN_Y`).
- `Makefile`: FPGA `FREQ` 31.5 -> 40.

## Testing

- Full gold-image rebuild — frame dimensions themselves change (800x600 vs.
  640x480), so all three golds are new captures, not tweaks. Look at them by
  eye before committing, per CLAUDE.md.
- Re-run `make -C test delay-sweep` at the new timing. The vsync-to-first-byte
  margin is a different number at this clock/blanking split and should be
  measured again, not assumed safe by analogy to the 640x480 figure.
- `make -C test IHP_SRAM=1` still applies even though the ASIC clock isn't
  changing, since the line buffer's addressing (64 cols exactly) is being
  exercised at its wall for the first time.

## Non-goals

- ASIC/`config.json`/hardening changes — separate decision after judging the
  FPGA result on hardware.
- Digit geometry redesign — reviewed and set aside (see above).
- Mitred/chamfered segment ends (`resolution_discussion.md` §5) — still needs
  >=4px segments, which this mode doesn't provide either.
